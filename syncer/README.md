# PearlPod syncer

Selected profile' audio playlists beginning with `PP:` are selected; the prefix is stripped for PearlPod. Source identity is the Plex playlist/track ID, not a display name. The host continuously prepares completed generations; PearlPod's Sync now discovers the host, starts its temporary FTP receiver and sends `POST /sync`. The host uses one lftp session, then uploads a catalog and ready marker last. Players requesting content progress receive an explicit playlist-ordered delta; older firmware retains the `mirror -R` path. No sync token, pairing or authentication is required. FTP uses anonymous protocol responses. The Plex token stays on the host.

## Local run

```sh
python3 -m venv .sync-venv
.sync-venv/bin/pip install -r syncer/requirements.txt
brew install lftp
.sync-venv/bin/python syncer/server.py --plex-token .sync-state/plex-token --music /Volumes/MUSIC --cache .sync-state/cache --advertise-ip 192.0.2.101
```

The IP is this Mac's observed LAN address for the spike; use the actual host address on another machine. The service advertises `_pearlpod-sync._tcp` on port 8787. PearlPod advertises `_pearlpod._tcp` during sync and accepts anonymous FTP on 2121, with passive data on 2024. mDNS locates the trigger service; file contents move through FTP. `GET /status` reports preparation and transfer state. The trigger destination is the caller's IPv4 address, not an arbitrary URL in the request. Only one transfer runs at a time. Background preparation runs about every minute, with capped backoff after failures, and retains the previous publication on error. A sync request is rejected with 503 while the first export is incomplete. Otherwise it receives 202 immediately, performs a fresh source check after the request, pins that complete generation and uploads it. Preparation and delivery share one lock. A failed fresh check produces a terminal FTP error marker rather than silently sending stale music. Fresh preparation, including time waiting for a poll, is bounded to 120 seconds; background preparation has a 600-second bound and retains completed cache work for retry. `/health` tests HTTP liveness independently of Plex; `/status` separates source freshness, preparation error and upload state. Plex outages do not prevent HTTP startup.

Plex paths `/share/Media/Music/...` map to `/Volumes/MUSIC/...` locally. Supply `--source-root` if Plex uses a different prefix. The exporter resolves exactly one media part, confines resolved files to the allowed mount, and refuses ambiguous/unavailable selections. The NAS music mount is read-only to the exporter. In Plex, use the `selected-profile` profile; the verified test list is `PP: PearlPod Sync Test` (12345), containing two accessible P!nk tracks. Plex's playlist-creation API collapsed the attempted repeated entry; the exporter preserves the ordered entries actually returned by Plex.

## Preparation and incremental transfer

Lossless input converts to 256 kbps, 48 kHz stereo MP3. Existing MP3 audio is stream-copied. ID3v2.3 tags include title, artist, album artist, album, track/disc, genre and available year; album covers are resized to at most 480 × 480 and embedded. Covers also exist as separate delivery objects. Embedding means a cover/tag change legitimately changes that MP3's file bytes and delivery hash; lyric-only and playlist-only edits do not change audio. Readable Artist/Album/NN - Title.mp3 card paths retain ordinary-player compatibility. A hidden `.pearl/delivered.json` receipt records host object identities after file delivery, independently of the ready marker cleared on each sync. Size comparisons reuse unchanged files; explicit replacement handles changed bytes of equal length. A missing/damaged receipt conservatively replaces equal-length existing files once. The Pod does not hash music. For content-aware sync, each playlist file follows its songs, artwork and lyrics; an atomic receipt checkpoint follows each completed playlist. The final receipt/catalog/ready writes follow delivery; ready is still last. Host preparation caches retain immutable object identities. Persistent source fingerprints avoid rehashing every NAS file on each poll; source size, modification/change time and identity changes invalidate the cached checksum. Prepared-object checksums are reused only while their file fingerprint is unchanged. Filesystem changes that deliberately preserve every fingerprint field require clearing the cache or an explicit integrity audit.

Same-stem LRC/SRT/VTT/TXT and language-qualified sidecars are carried over. Embedded untimed lyrics are extracted when no sidecar exists. Supported timed text normalizes to bounded UTF-8 LRC; originals remain separate assets. Lyrics are associated with the exact source track, not a global filename search. The initial device surface selects the first available language variant. Unsupported encodings or malformed/oversized text fail preparation and retain the old publication. Missing lyrics are fine.

The microSD uses readable artist/album folders, adjacent covers/lyrics and relative Playlists/Name.m3u8 files. Hidden `.pearl` data are bookkeeping. Catalog format 2 checks media paths/lengths, metadata/playlist references and complete candidate loading before committing active/previous catalog identifiers to NVS. Media contents are not hashed/read back. Interrupted files are retransferred as whole files; upload resume and block deltas are not claimed. The Pod reports free card bytes in its trigger. Recursive FTP inventory budgets only missing or mismatched files, catalog overhead and a reserve before upload. Insufficient space or failed write/close prevents activation. Readable uploads use temporary filenames and rename on success. A validated format-2 migration retires legacy hidden managed media; manually copied and readable music are preserved. Removing a selected playlist currently leaves ordinary music files on the card; ownership/deletion reconciliation remains future work. FAT/microSD power-cut recovery remains a physical acceptance gate.

## Player controls

Open Your library and scroll to Sync now. Pause music first. Sync has a finite WiFi/FTP session; servers and radio stop afterward. Sync shows the current playlist, song/album, overall changed-song count and a measured whole-sync ETA. Unknown totals hide the bar; stalled data replaces the estimate with a waiting message. Completed playlists and songs survive interruption in normal card folders; the next sync skips files confirmed by playlist receipts. A failed current file remains hidden and is retried from its beginning. The player rescans completed additions after cancellation/failure, and its normal startup scanner discovers them after reboot. Long power hold requests sync shutdown before sleeping. USB console commands are `sync`, `sync status`, and `sync source http://HOST:8787` for a configured-address fallback when multicast is unavailable. No source contact happens at boot.

Now Playing shows a Lyrics button when associated lyrics exist. Timed text follows the decoder-derived millisecond clock with previous/current/next lines; arrows/swipes browse and Follow resumes tracking. Untimed text scrolls. Track changes and screen sleep release lyric memory. Current fonts do not cover all Japanese characters, and DMA/MP3 timing alignment still needs physical measurement; word highlighting and language selection are not implemented.

## Small container

Build from the repository root: `docker build -t pearlpod-syncer:local -f syncer/Dockerfile .`. The Docker context excludes credentials, firmware backups, caches and other workspace files. The locally built image is approximately 216 MiB including Python, ffmpeg and lftp.

On the Linux NAS, set `PEARLPOD_MUSIC`, `PEARLPOD_CACHE`, `PEARLPOD_PLEX_TOKEN`, `PEARLPOD_HOST_IP` and optionally `PEARLPOD_UID`/`PEARLPOD_GID`, then run `docker compose -f syncer/compose.yaml up -d`. The cache must be writable by that UID; music and the token are read-only mounts. Host networking permits mDNS and return FTP connections. The October 3 automation execution deploys `pearlpod-syncer` on example NAS at LAN address `192.0.2.2`, through Portainer endpoint 2. Host storage is `/share/Container/pearlpod-syncer/cache` and `/share/Container/pearlpod-syncer/secrets/plex-token`; music is `/share/Media/Music`. The service runs as 1000:1000, with a read-only token and music mount. See [deployment and execution evidence](../docs/EXPORTER-AUTOMATION-EXECUTION.md). Nightly charging wake remains gated on a verified charging signal; manual sync is the firmware path.

## Portainer updates and rollback

`tools/deploy_syncer.py` reads a supplied `op://` Portainer credential reference at runtime. It never prints the key or embeds it in the image. Build a full image archive locally for first deployment or dependency/Dockerfile changes; Python-only updates can use `--source-dir syncer` against an already installed image. The tool verifies ownership of the existing container, keeps it stopped under a rollback name, creates the replacement and checks HTTP liveness. A known start/health failure restores the previous container. Source readiness and real sync remain separate acceptance checks. Inspect state before retrying a network timeout with an unknown outcome.

```sh
docker build --platform linux/amd64 -t pearlpod-syncer:automation -f syncer/Dockerfile .
docker save -o /tmp/pearl-syncer.tar pearlpod-syncer:automation
python3 tools/deploy_syncer.py --portainer-url https://192.0.2.2:9443 --endpoint 2 --portainer-token-reference "$PEARLPOD_PORTAINER_REFERENCE" --insecure --image-archive /tmp/pearl-syncer.tar --host-ip 192.0.2.2 --music /share/Media/Music --source-root /share/Media/Music --plex-url http://192.0.2.2:32400 --deployment-dir /share/Container/pearlpod-syncer
```

`--insecure` is specific to the observed NAS self-signed HTTPS certificate. First deployment also supplies `--plex-token-file` pointing to the existing Selected profile credential; updates reuse the NAS runtime file. For incremental updates replace `--image-archive /tmp/pearl-syncer.tar` with `--source-dir syncer`. Neither operation publishes an image to a registry. To roll back in Portainer, stop the current `pearlpod-syncer`, rename it out of the way, rename the selected retained rollback container to `pearlpod-syncer`, then start it. Avoid running two discovery advertisements simultaneously. Cache and token remain on the host across container recreation.

The default host cache budget is 20 GiB. Before a new transcode the exporter reserves an output allowance and checks actual free space. It retains current/previous publications and recent candidates; old unreferenced objects, unused preparation/source memos and abandoned temporary files are reclaimed exclusively while publication/delivery is locked. Active source memos are refreshed on reuse. A full budget fails preparation while preserving the previous head; it never deletes active card music to make room.

Warm export avoids repeat metadata/lyric/art processing through persistent per-track results, scans each album directory once per phase, fetches artwork with four workers and prepares changed tracks with two workers. The measured QNAP 91-track warm publication improved from 15.5 seconds to 2.63 seconds with an identical catalog. Source/sidecar/art/metadata fingerprints invalidate cached results when needed. Unique temporary files make concurrent preparation writes safe.
