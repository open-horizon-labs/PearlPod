# Embedded sync reuse — fact check, 2026-10-03

The previous comparison was incomplete. Small ESP32 file-sync code exists, and a standard embedded file server plus a NAS-side sync tool is an established approach on the same ESP32-S3 hardware family. The earlier search result (“I haven't found a turnkey ESP-IDF incremental-sync engine”) is a bounded observation, not evidence that no suitable implementation exists or that a custom HTTP downloader is the cheapest option. No candidate was compiled, installed or benchmarked on PearlPod during this review.

## Revised practical direction

Investigate **NAS Plex exporter → lftp mirror → native ESP-IDF FTP receiver on the Pod** before building a custom HTTP sync client. The standard host tool handles traversal, size/time comparisons and transfer retries; the device exposes a restricted managed staging area. HTTP pull remains a credible comparison candidate, especially for Pod-initiated sessions. There is still no measured winner on this device.

Use immutable prepared audio names and compare sizes while treating checksums as the final integrity test. Both [rclone FTP](https://rclone.org/ftp/#limitations) and ordinary size/time mirroring lack the required end-to-end checksum assurance. The Pod must validate completed assets and ordered M3U/catalog references, then activate a complete selection. A ready marker uploaded last is only an input to validation, not proof of success. Delete/retry a bad staged object so the host will not indefinitely skip a same-size corrupt file. Preserve the current selection until the replacement passes validation. This reuses transfer software while retaining the player-specific update boundary.

Do not copy FrameFi's script unchanged: it uses `--delete --only-missing` and logs completion without explicitly checking mirror failure. Deletion must be limited to disposable staging, and an existing partial file must not be treated as complete solely because its name is present. Credentials must be obtained at runtime rather than embedded into scripts or logs. This report does not run the script against any device.

An intermittently awake Pod also needs host coordination: start a finite receiver session from Sync now or a verified charging wake, notify a small NAS job, let the existing tool perform the copy, and stop networking after success/failure/deadline. The trigger can use the existing HTTP status/control channel; the files still move through a standard protocol. No permanent server or network-dependent boot is required by this design.

## High-risk unresolved claims

Actual stack/heap use, throughput, audio/SD contention, path confinement, full-card recovery and interrupted upload behavior are not established. The native-IDF example contains fixed-size path concatenation and a credential log statement; a reuse prototype must bound those paths and remove that logging. Authentication alone does not establish encryption or safe filesystem isolation. Neither FTP nor HTTP makes FAT32/microSD power-loss transactional.

## Claims requiring expert review

No external expert is required to select a bounded prototype. Claiming a production-safe openrsync port requires actual port/build/runtime review. Claiming safe automatic activation requires the existing device fault-injection gates.

## Source gaps

No live Listener-profile Plex export, candidate server build, host/client interoperability run or physical PearlPod sync test was performed. Search coverage included ESP32/ESP8266, Arduino, FreeRTOS and embedded rsync/rclone/librsync terms in web and GitHub repository search. Search absence is not a proof of nonexistence. ESP-Sync's observed last commit is 2019; native-IDF FTP and openrsync sources inspected here have 2026 commits, but commit freshness does not establish device reliability.

## Corrections to apply

Reopen the transport selection, add ESP-Sync/openrsync/librsync and FTP/lftp evidence, and test existing native-IDF reception before asserting custom HTTP sync is less work. Keep Plex specifics on the NAS. For the first receiver prototype, test large/Unicode files, no-op and three-file additions, repeated/shared playlist entries, interrupted and same-size-corrupt uploads, full card, malicious paths, stop/restart resource reclamation and unchanged offline startup. Test single-session lftp compatibility first; test rclone only with a demonstrated viable connection strategy. Do not claim resume until packet/byte accounting confirms it.
